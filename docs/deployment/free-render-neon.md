# Free deployment: Render + Neon

This deployment is intended for an internship demonstration, portfolio review, or short-lived test environment. It uses:

- Render Static Site for the React/Vite frontend.
- Render Free Web Service for the ASP.NET Core API.
- Neon Free Plan for PostgreSQL.
- Local Ollama for the AI demonstration only.

No secret belongs in Git, `render.yaml`, frontend variables, screenshots, or documentation.

## Free-tier limitations

Render's free API service sleeps after inactivity and can take about one minute to wake. Its filesystem is ephemeral, so uploaded attachments disappear after a restart, redeploy, or sleep cycle. Database records remain durable in Neon. The free Render instance does not have enough memory to run the configured Ollama model, so deployed AI analysis is intentionally disabled. Run the AI feature locally during the presentation.

Neon's free database has usage and storage limits but no fixed 30-day expiration. This is preferable to Render Free Postgres, which currently expires after 30 days.

## 1. Create the Neon database

1. Sign in at <https://console.neon.tech/> using GitHub or email.
2. Create a project named `it-help-desk` in a region near the Render service, preferably an EU region near Frankfurt.
3. Open **Connect** and select the **C# / Npgsql** connection-string format.
4. Copy the complete TLS-enabled connection string to a private password manager temporarily.
5. Never paste it into a tracked file.

Npgsql supports Neon's required SNI/TLS connection. Use the exact connection string supplied by Neon rather than manually removing its SSL settings.

## 2. Apply the database migrations explicitly

Application startup intentionally does not call `EnsureCreated`, `Migrate`, or database-reset logic. Apply the reviewed migrations from the local project before starting the deployed API.

In PowerShell, from the API directory:

```powershell
cd "C:\Users\CLICK ONCE\it-help-desk\server\HelpDesk.Api"
$env:ConnectionStrings__DefaultConnection = "YOUR_NEON_NPGSQL_CONNECTION_STRING"
dotnet ef database update --connection "$env:ConnectionStrings__DefaultConnection"
Remove-Item Env:ConnectionStrings__DefaultConnection
```

The command applies the existing migrations and seeded lookup/role rows. It does not create a user or password. Confirm success in Neon's Tables view.

## 3. Create the Render Blueprint

1. Push `render.yaml`, the backend `Dockerfile`, and `.dockerignore` to GitHub.
2. Sign in at <https://dashboard.render.com/> and connect the GitHub account that owns the repository.
3. Select **New > Blueprint**.
4. Choose the `it-help-desk` repository and the `main` branch.
5. Render detects the root `render.yaml` and proposes two services:
   - `it-help-desk-api`
   - `it-help-desk-client`

The Blueprint requests three manual values. Do not put quotation marks around them in the dashboard.

| Variable | Service | Value |
|---|---|---|
| `ConnectionStrings__DefaultConnection` | API | Exact Neon C#/Npgsql connection string |
| `Frontend__AllowedOrigins__0` | API | Final frontend origin, for example `https://it-help-desk-client.onrender.com` |
| `VITE_API_BASE_URL` | Client | Final API origin, for example `https://it-help-desk-api.onrender.com` |

Render may add a suffix when a service name is already taken. Use the actual URLs shown in the dashboard. Origins contain only scheme and host: no trailing slash and no path.

`Jwt__SecretKey` is generated by Render and is never stored in Git. Keep the value stable after deployment; changing it invalidates existing access tokens.

## 4. Resolve the first-deploy URL dependency

The frontend and API origins refer to each other. During Blueprint creation, use the expected `onrender.com` names. After Render assigns the services:

1. Copy the exact Static Site URL into the API's `Frontend__AllowedOrigins__0` variable.
2. Copy the exact Web Service URL into the client's `VITE_API_BASE_URL` variable.
3. Save the API variable so the API redeploys.
4. Trigger a fresh frontend deploy because Vite embeds its public API URL at build time.

Do not place secrets in `VITE_` variables. Every Vite variable is public browser code.

## 5. Verify the deployment

Test in this order:

1. Open `https://YOUR_API_HOST/healthz` and wait for a healthy response. A cold start can take about one minute.
2. Open the frontend `/register` route directly to verify the SPA rewrite.
3. Register an Employee through the normal form.
4. Sign in and create a ticket.
5. Refresh once and sign in again if needed; the current frontend session is intentionally memory-only.
6. Verify Dashboard, ticket list/detail, comments, notifications, and attachment behavior.
7. Verify SignalR negotiation and WebSocket/fallback traffic in browser developer tools.
8. Sign in as a separately provisioned support account to test assignment, status controls, Reports, exports, and Activity Log.
9. Verify `/openapi/v1.json` is not exposed in Production.

## 6. Production Admin account

The Development Admin bootstrap never runs in Production. This is intentional. Do not enable it, add a public privilege-escalation endpoint, or put an Admin password in Render variables expecting the development bootstrap to run.

For an internship demo, create and verify the required privileged account through an approved, one-time administrative process before presentation. Public registration must continue to create Employee users only. If no production-safe provisioning process has been approved, demonstrate support-only functionality locally with the Development Admin instead of weakening production authorization.

## 7. AI demonstration

The Blueprint sets `Ai__Provider=Disabled`, so the deployed API returns a safe unavailable response for AI analysis. This prevents accidental billing and avoids pretending that Ollama can run within Render's 512 MB free instance.

For the final presentation:

1. Run Ollama locally.
2. Run `ollama pull llama3.2:3b` once.
3. Configure `Ai:Provider` as `Ollama` in the ignored local settings.
4. Start the backend and frontend locally.
5. Demonstrate the AI summary, category recommendation, priority recommendation, and three-to-five troubleshooting steps locally.

## 8. Attachment warning

Render Free Web Services have no persistent disk. `/tmp/helpdesk-uploads` prevents permission failures but does not preserve files. Uploaded attachment database metadata can outlive the physical file after a restart. Treat attachment upload as a local-demo feature until object storage or a paid persistent disk is configured.

Do not upload important or sensitive files to the free deployment.

## 9. Troubleshooting

### API fails during startup

- Confirm all three required manual variables are present.
- Confirm the frontend origin is an absolute HTTPS origin without a wildcard or trailing slash.
- Confirm the JWT secret generated successfully.
- Confirm the Neon connection is in Npgsql format and retains required TLS settings.
- Confirm migrations were applied.

### Browser reports CORS errors

Compare the browser address exactly with `Frontend__AllowedOrigins__0`. Render preview URLs and the production Static Site URL are different origins.

### Login or API requests return 502 during first use

Wait for the free API service to wake, confirm `/healthz`, and retry. Do not add automatic polling designed to prevent the free service from sleeping.

### Direct navigation returns 404

Confirm the Render Static Site rewrite is `/*` to `/index.html` with action `Rewrite`.

### Attachment download becomes unavailable

The free API filesystem was restarted or redeployed. This is an expected free-tier limitation, not a database migration issue.

## 10. Pre-presentation checklist

- Wake the API several minutes before the presentation.
- Verify the Neon project has not reached its free limits.
- Test frontend and API URLs in a private browser window.
- Keep a local version ready for Ollama and attachment demonstrations.
- Prepare screenshots as a fallback for unreliable venue internet.
- Never display Render or Neon environment-variable screens during the presentation.
