01 · Purpose

System overview

The IT Help Desk & Ticketing Management System gives employees one place to report technical problems and gives support staff the tools to triage, assign, update, resolve, audit, and report on those requests.

Request management

Create structured requests with category, priority, description, attachments, comments, and a permanent ticket number.

Support operations

Assign eligible support users, update status, record internal notes, review activity, and preserve the complete history.

Visibility & insight

Use dashboards, notifications, reports, PDF/Excel exports, and optional AI suggestions to understand support work.

Core principle: the backend is authoritative. Menu visibility helps users, but every identity, ownership, role, and workflow rule is enforced by the API.

02 · First use

Quick start

  1. Create an account or sign in.
    Self-registration creates a normal Employee account. Users cannot select privileged roles during registration.
  2. Open the Dashboard.
    Review the ticket totals and recent tickets available to your account.
  3. Select Create Ticket.
    Enter a clear title, detailed description, category, and priority.
  4. Track the request.
    Open the ticket to add comments, attach files, review status, or see its history.
  5. Watch Notifications.
    Assignment, status, comments, attachments, and cancellation events can generate persistent notifications for relevant users.
  6. Sign out when finished.
    Use the logout icon next to the account name in the sidebar.
Page refresh behavior: authentication tokens are held only in memory for security. A full browser refresh may require you to sign in again.

03 · Access model

What each user can do

Ownership-scoped

Employee

  • Create tickets.
  • See and search tickets they created.
  • Edit their own non-terminal, non-cancelled tickets.
  • Add public comments to accessible tickets.
  • Upload and download allowed attachments on owned tickets.
  • Cancel their own non-terminal tickets.
  • See their own dashboard data and notifications.
Ownership-scoped

Manager

Manager currently follows the same ticket ownership rules as Employee. The role provides management presentation where applicable but does not grant support privileges.

  • Create and manage tickets they created.
  • See ownership-scoped dashboard data.
  • Add public comments and attachments under the same business-state rules as Employee.
Support staff

IT Support Agent

  • See organization-wide tickets and analytics.
  • Edit accessible ticket basics.
  • Assign tickets to active support users.
  • Move non-terminal tickets to any active status.
  • Add public comments and private internal notes.
  • Manage attachments across accessible tickets.
  • Use Reports, exports, and the global Activity Log.
  • Cancel tickets, while preserving their records.
Full support access

Admin

Admin includes all support capabilities and has the broadest workflow authority.

  • See and manage organization-wide support data.
  • Assign, change status, comment internally, cancel, report, export, and audit.
  • Reopen a ticket from a terminal status when required.
  • Use the optional AI Analysis feature on accessible tickets.
No permanent ticket deletion: even Admin cannot delete a ticket. Cancellation is the supported final action because it preserves the request, comments, attachments, and audit history.

06 · End-to-end workflow

Ticket lifecycle

Open→In Progress→Pending→Resolved→Closed

This is a typical path, not a mandatory sequence. From a non-terminal status, support staff may select any active status. Closed is currently the terminal workflow status. An Admin can reopen a terminal ticket; an IT Support Agent cannot.

  1. Submission: a signed-in user provides title, detailed description, category, and priority. The system creates a unique ticket number and starts it as Open.
  2. Triage: support reviews the description, priority, category, attachments, and history. Optional AI Analysis can provide advisory suggestions.
  3. Assignment: support selects an active Admin or IT Support Agent. Reassignment ends the previous assignment record but preserves its history.
  4. Collaboration: users add public comments; support may add internal notes visible only within the permitted support workflow.
  5. Progress: support changes status and may record a transition note. Each actual status change is appended to history.
  6. Completion: the request can reach Resolved and then Closed. Records remain available according to role visibility.

Cancellation workflow

Cancellation is separate from status. Cancelling sets a final cancellation timestamp, ends the current assignment, and preserves the actual workflow status. It does not create a “Cancelled” lookup status.

  • Employees and Managers may cancel only their own non-terminal ticket.
  • Support staff may cancel any accessible ticket, including a terminal one.
  • Repeated cancellation requests are safe and do not duplicate the action.
  • Cancelled tickets remain readable, but editing, assigning, status changes, and new uploads are blocked.
  • Support may still add an audit-closure comment.

07 · Working with tickets

Ticket features

Search, filters, sorting, and paging

The ticket list supports text search and filters for category, priority, status, creator, current assignee, and UTC creation dates where the interface exposes them. Sorting and paging are performed by the server, and list state is reflected in the URL for reliable navigation.

Editing

The Edit page changes only title, description, category, and priority. It cannot secretly change ownership, assignment, status, or identity. Owners cannot edit a terminal or cancelled ticket; support has broader edit access except that cancellation blocks edits for everyone.

Comments and internal notes

  • Public comments support communication on an accessible ticket.
  • Internal notes are available only to Admin and IT Support Agent.
  • Comment text is displayed as plain text—HTML and Markdown are not executed.
  • Support can add closure/audit comments after cancellation; ordinary users cannot.

Attachments

Allowed

PNG, JPG/JPEG, WEBP, PDF, TXT, DOCX, and XLSX. Maximum file size: 10 MB.

Protected

Downloads require authentication. Files are not exposed as public links, and storage paths/keys/hashes are never shown.

Employees and Managers can upload to owned, non-terminal, non-cancelled tickets. Support can upload across accessible active tickets. Support can delete accessible attachments; non-support users may delete only an attachment they uploaded to their own ticket. Attachment deletion is soft deletion.

File safety: the system validates size, extension, content type, and basic signatures, but antivirus scanning is not implemented. Do not upload untrusted files in a production environment.

08 · Analytics

Dashboard

The Dashboard presents backend-calculated information; the browser does not invent or recompute totals.

  • Summary KPIs: total, Open, In Progress, Pending, Resolved, Closed, Cancelled, Critical, and Unassigned.
  • Status, priority, and category breakdowns.
  • Six-month Created, Closed, and Cancelled trend.
  • Eight most recently updated visible tickets.
  • Accessible list/table alternatives near charts.

Admin and IT Support Agent see organization-wide data. Employee and Manager see only tickets they created. Cancelled tickets remain included in totals and in their actual status bucket, while also appearing in the separate Cancelled metric.

09 · Updates

Notifications

Notifications are stored persistently and may be refreshed in real time through SignalR. If the real-time connection is unavailable, the notification page and manual reload continue to work.

Events

Assignment, status change, public comment, internal comment, cancellation, and attachment-added events.

Recipient safety

Recipients come from saved ownership and assignment data. Users cannot choose arbitrary notification recipients.

  • The acting user is excluded from their own event notification.
  • Recipients are de-duplicated.
  • Unread count appears in the sidebar and bell.
  • Mark-one and mark-all operations are idempotent.
  • Expired notifications are hidden from normal lists/counts.

10 · Support reporting

Reports and exports

Reports are available only to Admin and IT Support Agent. Draft filters do not change the report until applied, helping ensure the visible report and downloaded export use the same filter set.

  • Summary metrics and safe breakdowns by status, priority, and category.
  • Bounded date trends.
  • Support-agent workload using display names and IDs, not private identity fields.
  • PDF export for presentation and printing.
  • Macro-free Excel export with Summary, Status, Priority, Categories, Trend, and Agent Workload sheets.
Export privacy: exports omit emails, credentials, tokens, comments/internal notes, attachment contents, and storage information. Files are generated in memory and returned directly rather than saved by the server.

11 · Traceability

Activity Log and ticket history

The system provides two related views:

  • Global Activity Log: read-only, paginated, and restricted to Admin and IT Support Agent.
  • Ticket activity timeline: shown only after the normal ticket visibility check, so owners can see permitted history for their tickets while support can see accessible organization-wide history.

Audit metadata uses an allowlist and records safe identifiers or changed-field names. It excludes comment bodies, internal-note text, cancellation reasons, filenames, file contents, storage paths, emails, passwords, tokens, secrets, and exception payloads.

Operational audit: activity writing is best effort. It is useful for this project’s operational traceability but is not a compliance-grade transactional audit system.

12 · Optional assistance

AI Ticket Analysis

The AI Analysis card appears inside ticket details and runs only when the user selects Analyze Ticket. It can provide:

  • A factual 2–4 sentence ticket summary.
  • A recommended category selected from active system categories.
  • A recommended priority selected from active system priorities.
  • Three to five actionable troubleshooting and verification suggestions.
Advisory only: AI never edits, assigns, changes status, comments, cancels, or applies its own recommendations. A human must review every suggestion.

The browser sends only the ticket ID to the backend. The backend retrieves the permitted ticket and sends only its title, description, and allowed lookup names to the selected provider. User identity details, tokens, attachments, comments, and internal notes are excluded.

Provider options

  • Ollama: free local model option. Ollama and the configured model must be installed and running on the backend computer.
  • OpenAI: requires a valid API key and separately funded API billing. ChatGPT Plus does not include API credit.

If AI is unavailable, normal ticket management continues without interruption.

13 · Safe usage

Security and privacy

Authentication

JWT access tokens and rotating refresh tokens protect API access. Identity and roles come from validated claims, never browser-supplied user IDs.

Passwords

Passwords are managed through ASP.NET Core Identity. They are never returned, logged, or manually hashed by application features.

Authorization

Ownership and support permissions are enforced on the server. Inaccessible tickets are often reported as not found to avoid revealing their existence.

Local configuration

Secrets belong only in ignored local settings or environment variables. Never commit API keys, JWT secrets, database passwords, or Admin credentials.

Good user practices

  • Use a unique password and do not share accounts.
  • Sign out on shared computers.
  • Do not paste passwords, tokens, or secret keys into tickets or comments.
  • Avoid uploading sensitive files unless the organization permits it.
  • Review the recipient and ticket before adding internal or public information.
  • Treat downloaded attachments as potentially untrusted.

14 · Know before deployment

Important limitations

  • A browser refresh can end the visible session because frontend tokens are memory-only.
  • No permanent ticket deletion exists.
  • No email, SMS, or browser-push notification channel is implemented.
  • Local attachments require persistent storage and do not include malware scanning.
  • Multi-server deployment requires SignalR scale-out and shared/object attachment storage.
  • Activity logging is best effort rather than compliance-grade.
  • AI is optional, provider-dependent, and may be slow when a local model first loads.
  • The Manager role is currently ownership-scoped and does not imply support access.
  • Production database migrations must be applied explicitly; startup does not migrate or reset the database.

15 · Help

Troubleshooting

I cannot sign in
Confirm the exact email address, password, and backend URL. Development Admin credentials come from the ignored local configuration, not the example placeholders. If the configured email already existed, bootstrap does not reset its password.
I refreshed and returned to Login
This is expected with the current memory-only browser session. Sign in again; no token is stored in localStorage, sessionStorage, or IndexedDB.
I cannot see Reports or Activity Log
Those pages require Admin or IT Support Agent. Employee and Manager roles do not receive support-only navigation or API access.
I cannot see another employee’s ticket
Employee and Manager access is restricted to tickets they created. Support staff can see organization-wide tickets.
I cannot edit, assign, upload, or change status
The ticket may be cancelled, terminal, outside your ownership, or the action may require a support role. The server’s current ticket state determines what is allowed.
AI Analysis says temporarily unavailable
For Ollama, confirm the Ollama application is running, the configured model is downloaded, and the backend was restarted after configuration changes. For OpenAI, verify the key, billing quota, model access, and network connectivity.
Notifications are not arriving immediately
Use the Notifications page or reload it. Persistent REST notifications work even if SignalR/WebSocket real-time hints are temporarily disconnected.
An attachment is rejected
Confirm it is 10 MB or smaller and uses an allowed extension and content type. Renaming an unsupported file does not make it valid.
